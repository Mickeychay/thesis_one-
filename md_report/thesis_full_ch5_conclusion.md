# บทที่ 5: สรุปผล อภิปราย และข้อเสนอแนะ (Conclusions, Discussion, and Future Work)

---

## 5.1 สรุปผลการตอบโจทย์วิจัย (Summary of Findings)

วิทยานิพนธ์ฉบับนี้พัฒนาระบบ **H2L** เพื่อใช้วิเคราะห์ข้อความกรณีศึกษาทางสังคมสงเคราะห์ โดยเชื่อมการตรวจจับปัญหา การควบคุมคำปฏิเสธ การค้นคืนเอกสาร และการอธิบายผลไว้ใน pipeline เดียวกัน ผลการทดลองรุ่นปัจจุบันตอบคำถามวิจัยได้ดังนี้

**คำถามวิจัยข้อ 1: H2L ในฐานะ problem-aware scoring layer ให้ผลด้าน retrieval แตกต่างจาก baseline อย่างไร**
คำตอบคือ **H2L ช่วยแตกต่างกันตามธรรมชาติของ backbone และไม่ได้เพิ่มค่า top-rank ทุกตัวแบบอัตโนมัติ** ผล unified proper evaluation ล่าสุดแสดงว่า H2L-BM25 ได้ nDCG@5 สูงสุดที่ 0.3171 พร้อมครอง P@5, MAP และ F1@5 สูงสุด ขณะที่ H2L-Hybrid ให้ MRR สูงสุดที่ 0.3444 และยก MAP/MRR เหนือ hybrid baseline ได้ แม้ nDCG@5 จะลดลงเล็กน้อย ส่วน H2L-HyDE รอบล่าสุดพลิกกลับมาดีกว่า HyDE เดิมในหลาย metric ขณะที่ H2L-Naive RAG ยังเป็นภาพแบบผสม จึงยืนยันว่า H2L เป็น context-sensitive reranking layer มากกว่าจะเป็น universal booster

**คำถามวิจัยข้อ 2: sentence polarity gate ภายในสถาปัตยกรรม H2L ช่วยลด false positive จากประโยคที่ต้องอาศัยการตีความเชิงบริบทได้หรือไม่**
คำตอบคือ **ได้ในระดับใช้งานได้จริง** โดยผลล่าสุดให้ Accuracy = 0.8667, NDR = 0.7222, FPR = 0.0877 และ F1 = 0.7222 ระบบตรวจพบเคสปฏิเสธได้ 13 จาก 18 เคส และลดน้ำหนักเคสยืนยันปัญหาผิดพลาด 5 จาก 57 เคส จึงกล่าวได้ว่ากลไก polarity ในรุ่นปัจจุบันช่วยลด false positive ได้จริง แต่ยังต้องพัฒนาต่อในกรณีภาษาซับซ้อนหรือข้าม clause

ชั้น explainability ของระบบไม่ได้ถูกตั้งเป็นคำถามวิจัยแยกต่างหากในฉบับปัจจุบัน แต่ทำหน้าที่เป็นหลักฐานสนับสนุนการตีความผลทั้งสองข้อ โดยช่วยให้ผู้วิจัยตรวจสอบได้ว่า H2L ปรับอันดับเอกสารเพราะอะไร และ polarity gate ลดหรือคง candidate ใดไว้ด้วยเหตุผลเชิงบริบทใด

## 5.2 อภิปรายผลเชิงวิชาการ (Discussion)

### 5.2.1 H2L ควรถูกมองเป็น scoring and safety layer มากกว่า retriever ตัวใหม่

ข้อค้นพบหลักของงานนี้คือ H2L ไม่ได้มีคุณค่าเพียงเพราะ "ชนะ" baseline ในตัวเลข retrieval บางตัว แต่มีคุณค่าเพราะทำหน้าที่เป็นชั้น problem-aware scoring และ safety control ที่ครอบบน retrieval backbone หลายแบบได้ ผลการทดลองแสดงชัดว่า H2L สามารถ

- ใช้ปัญหาที่ตรวจพบจากเคสจริงไปช่วยปรับอันดับเอกสาร
- ลด false positive จากคำปฏิเสธ
- แยกผลลัพธ์เป็น `confirmed`, `needs_review`, `verify_documents`, `filtered` เพื่อสื่อระดับความมั่นใจเชิงปฏิบัติการ
- เปิดเผยเหตุผลของการจัดอันดับผ่าน interactive traces

ดังนั้น แกนของผลงานวิจัยนี้จึงไม่ใช่การสร้าง retrieval backbone ใหม่ แต่เป็นการสร้างสถาปัตยกรรมที่เชื่อม detector, retrieval และ explanation เข้าด้วยกันอย่างตรวจสอบย้อนกลับได้

### 5.2.2 เหตุใด H2L จึงไม่ได้ทำให้ทุก metric ดีขึ้นทุก backbone

ผล retrieval ของงานนี้ให้ภาพที่สำคัญมากในเชิงวิชาการ คือการใช้ problem-aware signals และ polarity-aware scoring มีลักษณะเป็น **context-sensitive reranking** ไม่ใช่ universal booster การปรับอันดับเช่นนี้มีโอกาสทำให้เอกสารบางชิ้นที่เดิมติดอันดับต้นเพราะมีคำตรง ถูกลดลงเล็กน้อยหากบริบทของเคสไม่สนับสนุนมากพอ ขณะเดียวกันเอกสารที่สอดคล้องกับปัญหาจริงแต่เดิมอยู่ลึกกว่า อาจถูกดันขึ้นมาแทน

ด้วยเหตุนี้ จึงเห็นผลแบบต่างกันในแต่ละ backbone:

- BM25 ได้ประโยชน์ในเชิง incremental gain และยังเร็วมาก
- HyDE ในรอบประเมินล่าสุดกลับมาได้ผลดีกว่าเดิมเมื่อถูกครอบด้วย H2L แต่ยังมีต้นทุนเวลาเพิ่มอย่างมีนัยเชิงปฏิบัติ
- Dense retrieval มีภาพแบบผสม โดย MRR ดีขึ้นเล็กน้อยแต่ MAP และ top-rank ลดลงเล็กน้อย
- Hybrid baseline มีภาพค่อนข้างนิ่งในอันดับต้น แต่ H2L ช่วยยก MAP/MRR ได้ชัดกว่า backbone เดิม

ข้อสรุปนี้ช่วยอธิบายว่าเหตุใดผู้วิจัยไม่ควรตีความ H2L แบบง่าย ๆ ว่าเป็นโมดูลที่ "ต้องชนะทุกครั้ง" แต่ควรมองว่าเป็นกลไกที่ทำให้ระบบมีความปลอดภัยและตีความได้ดีขึ้น โดยที่ retrieval quality ส่วนใหญ่ยังอยู่ในระดับแข่งขันได้

### 5.2.3 เหตุใด H2L-Hybrid จึงยังเป็นคู่สำคัญที่สุดของวิทยานิพนธ์

แม้ H2L-BM25 จะได้ nDCG@5 สูงที่สุด แต่ `h2l-hybrid` ยังเป็นคู่ที่สำคัญที่สุดสำหรับวิทยานิพนธ์ด้วยเหตุผล 3 ประการ

1. เป็นตัวแทนของระบบเต็มที่รวม **detector + hybrid retrieval + sentence polarity + explanation stack**
2. ยังคง MAP และ MRR ได้ดีในระดับใกล้หรือสูงกว่า hybrid baseline
3. สอดคล้องกับเป้าหมายของงานที่ต้องการระบบใช้งานจริง ไม่ใช่เพียงตัวเลข retrieval สูงที่สุดในฉากทดลองเดียว

กล่าวอีกนัยหนึ่ง หากต้องเลือกโมเดลเพื่ออธิบาย "สถาปัตยกรรมที่เสนอ" ควรใช้ `h2l-hybrid` แต่หากต้องการชี้ให้เห็น "ตัวเลือกที่เบาและทำ retrieval ได้ดีที่สุดใน test split ปัจจุบัน" ควรอ้าง `h2l-bm25`

### 5.2.4 การแยก retrieval metrics ออกจาก safety metrics เป็นข้อดีของงานนี้

หนึ่งในจุดแข็งเชิงระเบียบวิธีของงานนี้คือการไม่บังคับรวม retrieval quality กับ sentence polarity safety เป็นตัวเลขเดียว เพราะสองสิ่งนี้ตอบคำถามคนละแบบ

- retrieval metrics ตอบว่าเอกสารถูกจัดอันดับดีหรือไม่
- safety metrics ตอบว่าระบบเข้าใจประโยคปฏิเสธและบริบทเสี่ยงผิดพลาดหรือไม่

การแยกสองมิตินี้ออกจากกันช่วยให้บทสรุปของวิทยานิพนธ์ตรงไปตรงมา และป้องกันการตีความผิดว่า retrieval score ที่สูงเท่ากับระบบปลอดภัยกว่า

### 5.2.5 บทบาทของ interactive explanation ต่อความพร้อมของงานวิทยานิพนธ์

ในงานรุ่นล่าสุด การอธิบายผลไม่ใช่เพียงองค์ประกอบเสริมของหน้าเว็บ แต่เป็นส่วนหนึ่งของหลักฐานวิจัย เพราะช่วยให้ตรวจสอบได้ว่า

- problem code ใดถูกจับเพราะ keyword หรือ context ใด
- polarity gate ลด candidate ใดและเพราะอะไร
- เหตุใดบางรหัสจึงถูกระบุเป็น `verify_documents` แทนที่จะถูกสรุปว่า confirmed
- document ใดสนับสนุน problem ใด
- final score ของเอกสารเกิดจากองค์ประกอบใดบ้าง
- ผลที่กำลังอ่านอยู่เป็นผลจาก `Case-Level Runtime Review` หรือ `Benchmark Performance Review`
- benchmark artifact ปัจจุบันพร้อมใช้อ้างอิงแล้วหรือยัง ผ่านส่วน `System Evaluation Status`

คุณลักษณะนี้ทำให้ระบบพร้อมกว่าสำหรับการนำเสนอในเชิงวิทยานิพนธ์ เพราะผู้อ่านสามารถไล่ตรวจเส้นทางการตัดสินใจของระบบได้จริง
ในรุ่นปัจจุบัน dashboard ยังอ่าน `evaluation-progress` และ stable latest/checkpoint aliases จากดิสก์โดยตรง ทำให้ผู้วิจัยเห็นได้ว่าการรัน evaluator ไปถึงขั้นใด ใช้ artifact ชุดใด และไม่ได้แสดงข้อมูลจำลองคั่นกลาง

พร้อมกันนี้ การปรับปรุงจากเคสภาษาจริงยังชี้ให้เห็นบทเรียนเชิงระเบียบวิธีที่สำคัญ คือ false positive จำนวนมากไม่ได้เกิดจากการขาด keyword แต่เกิดจากการผูก evidence ผิดช่วง ผิดคน หรือผิดระดับความมั่นใจ งานรุ่นล่าสุดจึงเสริม clause-local polarity, sentence-bound evidence, coreference binding, code-specific context rules, implicit taxonomy-anchor guard และ exact duplicate de-dup เช่นการกันการสรุปประเด็นไร้ที่อยู่อาศัยซ้ำทั้ง `0801` และ `Z59.0` การเปลี่ยนแปลงเหล่านี้ไม่ได้มีผลเพียงต่อหน้า UI แต่ทำให้ detector มีพฤติกรรมสอดคล้องกับการอ่านของผู้เชี่ยวชาญมากขึ้นในเคสจริง

## 5.3 ข้อจำกัดของการวิจัย (Limitations)

1. **ขนาด test set ยังไม่ใหญ่พอสำหรับสรุปผลเชิง retrieval อย่างเด็ดขาด**
   การเปรียบเทียบ baseline vs H2L ในชุดทดสอบ 75 เคสให้แนวโน้มที่น่าสนใจ แต่ยังไม่มากพอให้ใช้ pair-level significance เป็นฐานข้อสรุปหลักของทุก backbone ดังนั้นวิทยานิพนธ์ฉบับนี้จึงยึด unified evaluation และการตีความเชิง pattern ของหลาย metric ร่วมกัน มากกว่าฟันธงจากการทดสอบนัยสำคัญเชิงคู่เพียงอย่างเดียว

2. **ชุดเคสปฏิเสธปัญหามีเพียง 18 เคส**
   แม้เพียงพอสำหรับแสดง proof of concept ด้าน sentence polarity แต่ยังน้อยสำหรับการสรุป generalization ของภาษาไทยในทุกบริบท

3. **ระบบยังพึ่ง taxonomy และกฎเชิงบริบทในระดับหนึ่ง**
   แม้พยายามลด hard-coding โดยใช้ actor-target-action, clause logic, coreference heuristics และ L2 semantic validation แต่การครอบคลุมคำสแลง ภาษาไม่เป็นทางการ ภาษาถิ่น และตัวอ้างอิงหลายคนในย่อหน้าเดียวกันยังเป็นข้อจำกัด

4. **ผล retrieval หลักของบทนี้ใช้ `detected problems` ไม่ใช่ `gold problems`**
   ดังนั้น retrieval score จึงสะท้อนระบบแบบ end-to-end มากกว่าศักยภาพสูงสุดของ retriever เพียงอย่างเดียว

5. **latency ของบางกลยุทธ์ยังสูง**
   โดยเฉพาะ HyDE และ H2L-Hybrid ซึ่งมีต้นทุนด้านเวลาเหนือกว่า BM25 หรือ dense retrieval ธรรมดาอย่างชัดเจน

## 5.4 ภัยคุกคามต่อความเที่ยงตรงของงานวิจัย (Threats to Validity)

เพื่อให้การสรุปผลของวิทยานิพนธ์ระมัดระวังและตรวจสอบได้ ผู้วิจัยพิจารณาภัยคุกคามต่อความเที่ยงตรงของงานใน 3 มิติหลัก ดังนี้

### 5.4.1 Internal Validity

ภัยคุกคามด้านนี้อยู่ที่ความเป็นไปได้ที่ผล retrieval จะเปลี่ยนเพราะ **detector** มากกว่าที่จะเปลี่ยนเพราะ **retriever หรือ H2L scoring** เอง เนื่องจากผลหลักของบทนี้ใช้ `detected problems` แบบ end-to-end จึงมีโอกาสที่ detector gap จะส่งผลต่อคะแนน retrieval โดยตรง ผู้วิจัยจึงต้องอ่านผล `gold problems` เป็น upper-bound diagnostic และไม่ตีความว่าคะแนน retrieval ที่ลดลงเล็กน้อยหมายถึง retriever อ่อนลงเสมอไป

### 5.4.2 Construct Validity

ภัยคุกคามด้านนี้อยู่ที่การที่ retrieval metric เช่น MAP, MRR และ nDCG วัด **relevance ของเอกสารตาม ground truth** แต่ H2L ถูกออกแบบให้เป็น **problem-aware scoring and safety layer** ดังนั้นบางกรณี H2L อาจดันเอกสารที่สอดคล้องกับปัญหาสังคมของเคสขึ้นมา แม้เอกสารนั้นจะไม่ได้ให้ค่า retrieval metric สูงขึ้นทันทีในอันดับต้น ๆ ผู้วิจัยจึงแยกการรายงานเป็นสองมิติ คือ

- retrieval quality
- safety / sentence polarity

การแยกสองมิตินี้ช่วยลดการตีความผิดว่าค่า rank metric เพียงอย่างเดียวสามารถแทนคุณค่าทั้งหมดของระบบได้

### 5.4.3 External Validity

ภัยคุกคามด้านนี้อยู่ที่ขนาดและความหลากหลายของข้อมูล โดยเฉพาะ

- test set มีเพียง 75 เคส
- เคสปฏิเสธปัญหามี 18 เคส
- ภาษาในงานยังไม่ครอบคลุมภาษาถิ่น ภาษาปาก หรือสำนวนซับซ้อนทุกแบบของภาษาไทย

ดังนั้น ผลของงานนี้ควรถูกตีความว่าเป็นหลักฐานเชิงประจักษ์ในระดับที่น่าเชื่อถือสำหรับระบบต้นแบบวิจัย มากกว่าจะอ้าง generalization ต่อทุกบริบทของงานสังคมสงเคราะห์ไทยโดยสมบูรณ์

การระบุ threats to validity อย่างชัดเจนทำให้ข้อสรุปของวิทยานิพนธ์มีความสมดุลขึ้น กล่าวคือผู้วิจัยสามารถยืนยันสิ่งที่ระบบทำได้จริง พร้อมยอมรับขอบเขตที่ยังต้องพัฒนาต่ออย่างตรงไปตรงมา

## 5.5 ข้อเสนอแนะสำหรับการวิจัยในอนาคต (Future Work)

1. **เพิ่มการประเมินแบบ gold problems vs detected problems ควบคู่กัน**
   เพื่อแยกให้ชัดว่าคะแนน retrieval ลดหรือเพิ่มเพราะ detector หรือเพราะ retriever

2. **ขยาย test set และ polarity benchmark**
   ควรเพิ่มทั้งจำนวนเคสและความหลากหลายของภาษา โดยเฉพาะภาษาปาก ภาษาถิ่น และเคสที่มีหลาย clause ซ้อนกัน

3. **เพิ่ม expert validation อย่างเป็นระบบ**
   ใช้ผู้เชี่ยวชาญหลายคนประเมิน correctness ของ problem detection, polarity reasoning และ evidence relevance เพื่อเสริมมิติภาคสนามให้วิทยานิพนธ์

4. **พัฒนาการจัดการ coreference และ event semantics ให้ลึกขึ้น**
   แม้งานปัจจุบันจะดีขึ้นมากในเรื่อง clause boundary, passive/active pattern และ actor-target-action แต่ยังสามารถต่อยอดด้วย learned coreference models, structured semantic parsing หรือ entity linking กับบทบาทเชิงสังคมได้

5. **ทำ per-code calibration สำหรับ review status**
   เนื่องจากระบบมีสถานะ `confirmed`, `needs_review`, `verify_documents`, `filtered` แล้ว งานต่อไปควรปรับเกณฑ์รายรหัสและประเมินกับเคสจริงว่ารหัสใดควรถูกจัดเป็น verify-documents โดย default

6. **แยก production mode และ research mode ให้ชัดขึ้น**
   production mode อาจเน้น latency ต่ำและความเรียบง่าย ส่วน research mode อาจเปิดการแสดง traces, ablations และ top-k exploration มากขึ้น

7. **ใช้ interactive report เป็นเครื่องมือเก็บ feedback จากผู้เชี่ยวชาญ**
   เนื่องจากระบบมี Live Execution Path, Case H2L Summary, H2L Document Score Breakdown, Problem-Document Matrix, Semantic Evidence Map และ Performance Provenance อยู่แล้ว งานในอนาคตสามารถต่อยอดให้ใช้เป็น annotation interface ได้

## 5.6 บทสรุปสุดท้าย (Final Concluding Remarks)

วิทยานิพนธ์ฉบับนี้แสดงให้เห็นว่า การทำระบบช่วยคัดกรองปัญหาสังคมจากข้อความภาษาไทยที่ดี ไม่ใช่การไล่เพิ่มพลังให้ retriever เพียงอย่างเดียว แต่ต้องจัดการทั้ง **problem detection, sentence polarity, retrieval ranking และ explainability** ไปพร้อมกัน

H2L ในรุ่นปัจจุบันยังไม่ได้พิสูจน์ว่าชนะทุก baseline อย่างมีนัยสำคัญทางสถิติในทุก metric แต่ได้พิสูจน์สิ่งที่สำคัญไม่แพ้กัน คือ

- ระบบสามารถลด false positive จากคำปฏิเสธได้จริง
- ระบบสามารถครอบบน retrieval backbone หลายแบบได้
- ระบบมีโมเดลหลักที่เหมาะใช้สรุปผลเชิงวิทยานิพนธ์ (`h2l-hybrid`)
- ระบบมีชั้นการอธิบายผลที่ตรวจสอบย้อนกลับได้ชัดเจนกว่างาน retrieval ทั่วไป

หากพิจารณาในภาพรวม งานนี้จึงมีคุณค่าทั้งในเชิงระบบและเชิงระเบียบวิธี โดยเสนอว่าระบบคัดกรองข้อความที่ดีสำหรับบริบทสังคมสงเคราะห์ไม่ควรวัดกันแค่ retrieval score เพียงตัวเดียว แต่ควรวัดร่วมกับความปลอดภัยและความสามารถในการอธิบายผลด้วย ซึ่งเป็นหัวใจของการนำ AI ไปใช้ในงานที่มีผลกระทบต่อมนุษย์จริง
